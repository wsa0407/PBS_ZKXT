## 适用范围与权限

所有角色可使用本技能理解或检查需求拆解。只有当前获授权的角色和活动可以调用 submit_requirements；其他角色回查依据、形成差异建议或咨询材料专家。加载本技能不会授权生成场景或 PBS，也不强制转入下一阶段。

## 阅读与拆解

先查看材料目录、处理覆盖和现有需求。完整拆解用 read_document_batch 按原文顺序读取，沿 next_cursor 与 document_version 继续到结束。list_document_sections 查目录，read_evidence 回查原文与上下文，search_evidence 辅助定位。局部咨询围绕所问范围核查，不强制重读全文，不宣称全文覆盖。

需求主体已明确但数量或边界未知时，保存有依据的部分并关联问题；无法判断是否构成要求时，可先保存独立待判断问题。场景是其他视角的组织成果，发现需场景解释的内容时提出具体问题，不在抽取技能中自动执行场景生成。

按需识别目标、提出/使用角色、作用对象、条件与缺口。维度用于理解材料，不是每条需求的必填表；未提及不等于不存在，也不必逐项生成澄清。遇到系统或设备名，保留客户明确指定的对象，同时核对其业务用途；意图未知时不以经验代填，更不能因追求抽象而删掉明确的型号或指标要求。

区分材料用途：政策目标或历史方案不自动成为本项目采购要求；访谈中“希望/考虑”不升级为承诺；现场记录证明其记录范围内的情况，不自动代表全区域现状。通用要求对本项目的适用性需有依据。必要的背景保存为背景，只有分析用途的参考片段可说明用途与不形成需求的原因，不为完成覆盖批量制造功能条目。

按文档逐批处理，通常最多 60 个短片段或 6000 字；长片段可以跨批读取，沿游标继续，不能遗漏余文。每批可分多次submit_requirements提交，每次最多30项。一条需求只讲一件事，保留数字、范围、否定、对象、条件与要求强度。quote 从所关联片段逐字连续复制。招标文件只保存有原文依据的要求，inferred=false；涉及解释的假设另记为疑点或建议，不提交为招标需求。非招标材料的推断使用 inferred=true，仍须保留支持推断的原文，不代表客户已确认。

类别：功能、性能、环境、安全、信创、集成、实施、服务、商务、资质、背景、范围外。不要把商务/资质条款混作产品功能。优先级为必须、重要、一般，依据原文措辞与标记说明判断；★、▲ 的含义不明确时记录待核对，不能仅凭符号认定强制要求或废标条件。系统可能要求重点审阅，不代表已核实其招标含义。

角色、对象、场景、缺口是分析维度，不是新增 category 枚举。数据共享与接口按实际要求归入集成等受支持类别，安全、性能、实施等约束分别保留；不能把“待澄清”写进 category 代替独立问题。

## 保存与核对

submit_requirements 接收 operation_id、document_id、document_version 和 requirements。每项含 evidence_id、text、quote、category、priority；params 可按 project_state 的参数字典提供 name/value/quote，不自行换算单位或推导数量。具体字段与限额以当前工具 schema 为准。

无实际要求的页码、目录、空白表格可用 ignored 提交 evidence_id 与具体 reason，不得用忽略绕过实质技术或商务条款。提交工具返回 accepted、errors、coverage；仅修复 errors 的内容，不重复已经成功的项。

提交前按需读取相邻内容，理解表格续行。quote 必须来自所关联真实片段，并足以支撑本条需求。若跨片段的完整表述无法被当前单片段引用契约承载，保留各段可核实的要求及关系说明，记录证据表示的限制；不要把系统引用限制误报为客户没有说清，也不能补造省略指标。

完整抽取结束需要所有实质片段有需求或有说明的处理记录；run_report 显示未处理片段时继续分页。已通过但未人工确认的需求均为初稿。对无法核实的引用保留待办，不伪造证据。
