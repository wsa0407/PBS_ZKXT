# PBS 场景性需求设计

本轮目标是让业务人员检查和修正“客户原文 → 原始需求 → 场景性需求 → 待确认问题”，并让已有产品匹配与 PBS 使用这些结果。业务流程采用 Workflow，分析由模型完成；需要多轮检索的 Agent 能力留在后续迭代。

业务范围依据本次讨论确定。以下数据与交互细节为待评审设计；本文不代表功能已经实现，也不代表样例已通过业务验收。

配套文件：

- [拆分示例与验收方法](2026-10-20-scenario-requirements-acceptance.md)
- [可核对原文的验收案例](2026-10-20-scenario-requirements-cases.json)

## 本轮范围

本轮完成场景独立保存、来源映射、审阅编辑、合并拆分、澄清关联、变更影响标记，以及向已有匹配流程传递场景上下文。用户可以先生成包含未知事项的草稿，随后逐项完善。

产品能力匹配矩阵、自动组合产品、多轮 Agent 检索、完整 BOM、行业配置平台不在本轮范围。已有产品目录、检索与数量规则继续作为下游基础。

三个实现方向的比较：

| 方向 | 优点 | 代价或不足 |
| --- | --- | --- |
| 给现有业务能力增加几个场景字段 | 改动较小 | 难以表达一个场景中的多项需求，以及多个场景共用一项能力 |
| 独立保存场景，与原始需求建立关联 | 能表达客户业务过程，支持审阅与追溯 | 需要增加数据对象、接口和一个工作页 |
| 同时重构场景、能力库、匹配矩阵与 Agent | 能统一设计整条链路 | 变更面大，难以定位质量提升来自哪里 |

本轮采用第二种。已有“业务能力”可以作为匹配适配数据，不增加一个必须由用户重复确认的阶段。

## 当前代码与目标的差距

| 当前实现 | 本轮调整 |
| --- | --- |
| `app/engine/capability.mjs` 输出 5W 场景和业务能力；场景没有独立 ID、原始需求关联或审阅状态 | 场景成为独立对象，关联实际存在的需求与证据 |
| `generateCapabilities` 把场景存入 `projects.pbs_meta.capabilities.scenes` | 场景独立持久化，PBS 元数据更新不影响场景 |
| `generateProjectPbs` 可以直接按原始需求匹配产品 | 新流程显式传入场景、具体需求、约束、未知事项和来源 |
| 项目工作页只有材料、需求、澄清、PBS、导出 | 增加“场景需求”页，原始需求和澄清页提供双向跳转 |
| 编号条款解析忽略没有编号的续行 | 保留条款续文与位置，避免限制条件在抽取前丢失 |
| 需求变更与证据重建存在状态和引用一致性问题 | 修改影响沿关联传播；证据身份与检索索引解耦 |

现有项目和人工修改必须保留。历史场景仅可作为迁移线索，不能推定其已经获得人工确认。

## 业务对象和拆分粒度

原始需求表达材料中的一项要求，保留数字、对象、范围、条件和要求强度。一个条款可以拆成多项原始需求，它们允许引用同一段原文。

场景表达特定角色在特定条件下，为达成业务目标所进行的一组活动。场景里的具体需求引用原始需求；生成的业务表述不能覆盖原文。

例：“夜间道路巡逻与事件发现”是场景，“识别交通事故”“识别违停”是具体要求。“红外吊舱”“产品 P06”属于实现选择，在产品匹配阶段处理。

拆分与合并遵循以下规则：

1. 能独立启动、独立完成并验收的业务目标，通常拆成不同场景。例如定时巡逻与接警后飞抵现场。
2. 为同一目标连续执行的步骤，通常保留在同一场景。例如火点告警的位置推送与护林员通知。
3. 白天和夜间可作为同一场景的条件变体；只有活动、约束或验收方式存在实质差异时才拆分。
4. 不用产品目录反推客户场景，不把每个功能词机械地变成一个场景。
5. 拆分方案可以有多种合理答案，验收比较信息保留、目标完整性与对应关系，不要求标题和场景数量完全一致。
6. 材料没有给出的角色、异常处置、时限和指标保持未知。分析建议可以提出，但要与客户要求分别展示。

## 场景性需求结构

场景由一个概要和一组关联的具体需求组成。优先级从关联要求展示，不把整个场景提升为统一强制级别。

| 字段 | 含义 | 规则 |
| --- | --- | --- |
| `id` | 项目内稳定编号，如 SC001 | 系统分配，归档后不复用 |
| `name` | 场景名称 | 描述业务目标，不使用产品型号 |
| `goal` | 期望实现的业务目标 | 保留直接依据或推断标记 |
| `actors` | 发起、执行、接收结果的角色 | 未明确的角色保留未知 |
| `context` | 地点、时间、业务条件 | 已知与未知分开记录 |
| `trigger` | 场景如何开始 | 定时、事件触发或人工发起等 |
| `activities` | 有序业务活动 | 每项引用支持它的原始需求 |
| `outcomes` | 预期结果及已有验收条件 | 不自行补充成功率、时限等数字 |
| `boundaries` | 范围、依赖、明确排除内容 | 不把建议自动纳入交付范围 |
| `assumptions` | 为解释场景提出的推断 | 包含理由、证据、确认状态 |
| `review_status` | 待确认、已确认、待复核、已归档 | 与问题是否解决分开 |
| `revision` | 当前内容版本 | 实质修改递增 |
| `origin`、`edited` | 系统生成、人工新增及人工修改记录 | 重生成保护人工成果 |

证据按照字段或活动关联，使用 `field_path` 指向被支持的内容。例如“林区”有原文依据，不代表同一场景中假设的告警时限也有依据。

证据至少包含：材料 ID、来源片段 ID、原文引用、材料内容版本及定位信息。当前文本材料支持片段编号与文本偏移；仅在解析器确实提供时记录 PDF 页码，不能生成虚构页码。

引用原文逐字可定位，只说明引用有效。系统还需检查该引用是否支持对应表述，语义正确性最终由业务人员审阅。

## 关联和覆盖

场景与原始需求为多对多关系，每个关联记录用途及必要说明：

| 关联用途 | 例子 |
| --- | --- |
| 核心要求 | 火点位置与告警推送 |
| 支撑要求 | 实时视频供现场人员查看 |
| 适用约束 | 数据存放位置、运行温度、接口条件 |

“未知事项”“尚未归入场景”通过问题和覆盖状态表达，不能伪造一个确定关联填满覆盖率。

原始需求有独立的处理去向：场景关联、跨场景约束、交付与服务、商务与资质、背景、范围外、待归类。部分满足多个用途时保留全部关联，覆盖统计按照原始需求 ID 去重。

跨场景约束记录适用范围，可指向若干场景或整个项目。性能、集成、安全类需求是否属于跨场景约束，要根据语义判断，不能仅按类别整体分流。

培训、驻场、运维等继续进入交付与服务清单，并传给 PBS。商务资格和付款条件保留在要求清单中，不虚构成软件功能或产品采购项。

页面区分：

- 处理去向是否明确；
- 原文引用是否有效；
- 内容是否已由人工确认；
- 下游是否已有响应。

有去向不等于已经满足需求。

## 生成和审阅流程

1. 读取材料、原始需求及已有澄清，构造带来源的分析上下文。保留原文条件、范围和要求强度。
2. 为原始需求提出处理去向，归纳场景和活动，关联具体要求；提出待确认事项与分析建议。
3. 校验引用、关联 ID、字段类型、重复内容及跨项目引用。引用不存在、无依据数字等错误进入问题清单，不能静默丢弃后宣告完成。
4. 事务性保存场景草稿、关联、问题和生成记录。模型调用失败时保留上一次完整结果。
5. 业务人员浏览场景，检查原文，编辑、合并、拆分、归档或确认。保存修改和确认是两个明确动作。
6. 场景和约束作为下游匹配上下文；问题继续随结果展示。

使用有输入输出约束的模型调用和校验修订即可完成第一版。默认一次生成；只有结构校验失败时允许一次修正。仍不合格则展示失败原因和原有结果，避免无限循环。

已确认场景可以存在已知未解决问题，页面必须显示这些问题。场景“已确认”表示业务人员认可当前描述和未知事项，并不代表相关交付条件已全部落实。

事实冲突影响的匹配、数量或交付结论必须保持待确认。无关部分仍可继续生成草稿。

## 页面与操作

在“需求”和“澄清”之间增加“场景需求”页，使用现有 Vue 与 ElementPlus 工作区。

列表展示名称、目标、关联需求数量、审阅状态、未解决问题数和下游待复核提示。详情展示业务活动、具体要求、约束、问题和来源。

主要操作：

- 生成场景草稿；已有人工成果时显示保留与新增结果。
- 新增、修改、确认、归档、恢复。
- 合并选定场景或拆分一个场景；用户检查关联重新分配和未承接内容。
- 从具体要求打开原文，从原始需求查看其全部场景。
- 在场景里提出问题、进入已有澄清页面，并查看已应用的答复。

需求页增加“关联场景”和“处理去向”；澄清页增加“关联场景”和“受影响字段”；PBS 中能够回溯场景、具体要求与原文。

## 澄清和变更

问题保留 `req_ids`，新增 `scenario_ids` 和可选 `field_paths`。客户答复先形成变更建议，明确展示原值、新值和依据，由用户选择应用。

应用答复后在同一事务中保存：

- 答复原文、来源和时间；
- 受影响需求或场景的新版本；
- 原文到答复的证据关系；
- 关联下游的待复核状态及原因。

客户答复与正式标书冲突时，保留两种说法并提示冲突，不能按时间先后自动覆盖正式条款。应用建议时需要明确记录如何处理该冲突。

修改需求、来源失效、场景合并拆分都会沿关联标记场景及 PBS 待复核，并取消相关 PBS 的已确认标记。无关对象保持原状。

重生成不会覆盖人工新增、修改、确认、归档的对象。未人工处理的旧草稿也不物理删除：新版本明确替代旧版本，旧 ID 保留供历史关联访问。不能通过复用编号使旧引用悄悄指向新内容。

合并和拆分使用新场景 ID，保存 `supersedes` 关系，将旧场景归档。新对象和重新分配的关联须复核；不把旧场景确认状态复制给新场景。

## 数据和接口边界

建议新增四类持久化记录：

- `scenarios`：场景当前内容、来源标记、审阅状态、版本。
- `scenario_requirements`：场景到原始需求的关联用途。
- `scenario_revisions`：修改快照、操作者、原因、前置版本及替代关系。
- `requirement_dispositions`：需求处理去向、适用范围、说明与审阅状态。

字段证据与场景内容一起保存版本快照；澄清问题扩展场景与字段关联。PBS 新增场景关联，保留原始需求关联。

接口沿用项目级服务：

| 操作 | 接口建议 |
| --- | --- |
| 读取场景与覆盖情况 | 现有项目详情响应增加 `scenarios`、`dispositions`、`scenarioCoverage` |
| 生成 | `POST /api/projects/:id/scenarios/generate` |
| 新增 | `POST /api/projects/:id/scenarios` |
| 编辑、归档、恢复 | `PUT /api/projects/:id/scenarios/:code` |
| 确认 | `POST /api/projects/:id/scenarios/confirm` |
| 合并、拆分 | `POST /api/projects/:id/scenarios/merge`、`POST /api/projects/:id/scenarios/:code/split` |

编辑、确认、合并和拆分请求携带读取时的版本号；版本不一致返回冲突并要求重新加载，防止覆盖其他修改。所有关联验证项目归属，写入统一经过服务层。对话动作调用同一服务，不绕过校验。

原始需求重抽取也必须遵循稳定 ID 与保留历史关系规则。删除材料时保留已被使用的来源快照并标记当前来源失效。

已有产品证据采用稳定身份及内容快照，检索索引可以重建。证据内容变化时，历史 PBS 保留当时依据，并显示需要复核，不能把旧证据替换成新的同名内容。

## 兼容与失败处理

数据库迁移为增量迁移，不清空材料、需求、问题、人工 PBS。旧项目显示“尚未生成场景需求”，用户可以继续查看与导出旧结果；进入新流程后生成场景草稿，不自动宣称旧 PBS 已完成场景匹配。

旧场景字段如果仍存在，可提取为待复核草稿；没有明确来源关系的内容只作为迁移提示，不创建推定来源关联。

生成中断不写入部分场景。重试具有请求标识，已经完成的请求不重复插入。保存步骤和失败原因，用户重试时复用已完成的材料解析结果。

未知字段不默认填零；空字段在界面显示“未明确”。缺少角色或触发条件不阻止保存草稿，但在场景详情显式提示。

## 开发顺序与验收

| 批次 | 主要工作 | 完成条件 |
| --- | --- | --- |
| A | 修复条款续行、元数据覆盖、待复核与证据身份问题 | 新增针对性回归通过，已有人工内容保留 |
| B | 场景、关联、版本、处理去向与增量迁移 | 老数据库迁移通过，ID 与多对多关系正确 |
| C | 场景生成、页面审阅、合并拆分与澄清 | 用户能完成一次从材料到修正场景的流程 |
| D | 场景上下文接入 PBS、影响传播和追溯展示 | 场景变更只影响相关结果，PBS 能回到原文 |

结构性验证覆盖编号续行、共享证据、未知值、非法引用、数据迁移、重生成保留、确认状态、合并拆分、澄清应用和局部影响传播。

模型质量按配套案例人工评分。记录模型、提示词版本、材料版本、输出、耗时和问题，不使用模拟模型测试通过数代表真实需求理解质量。

同一套输入比较优化前后：关键要求是否保留，原文和场景是否对应，是否补造客户事实，哪些疑问有业务价值，以及人工修改工作量。第一版只在样例中验收，真实项目上线前还需用脱敏实际材料校准。
