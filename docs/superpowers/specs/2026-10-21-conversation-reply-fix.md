# 专家对话回显修正

## 诊断

截图对应项目 `mvh7d1fv8ehc` 的消息 75，原文为 `@材料拆解专家 嘛呢`，记录时间为 2026-10-21 05:41:58（北京时间）。该条记录仍走旧的 intervention 路径，接收者为 understanding；当前预览进程启动于 05:46:26。不能把历史错误投递改写成材料专家曾经答复，也不能据此判断当前 @ 解析仍然失效。

底层确实调用官方 dsh 的角色会话和 Agent Loop，表现失真的原因在应用包装层：

- 宿主生成的 activity、delivery 状态被保存并渲染为专家聊天气泡。
- intervention 活动展示的是 acknowledge_intervention 的 explanation，实际模型 finalResponse 没有进入聊天。
- 普通聊天仍注入整个业务阶段目标；认领提示又将一般问候交给需求理解专家，没有区分明确 @。
- 在已有需求理解任务中回答问候后，仍可能再次触发需求理解确认请求。

## 修正

1. 在消息上保存由接收目标推导的 addressed 标记。明确指定的专家自行回应招呼；无 @ 的全局问候才由需求理解专家认领。现有 @ 解析仍优先于旧客户端的 target 字段。
2. 普通 discussion 不注入全阶段执行目标，不要求重新生成成果。共享 AGENTS 和工具说明区分自然对话、执行工作和内部处理回执。
3. 完成 intervention 后发布模型实际 finalResponse；无最终答复时才以简短处理说明兜底。保留必要引用、待确认或待澄清状态。
4. 旧运行与送达事件、内部处理回执保留在审计记录中，聊天投影过滤这些内部事件。对旧 activity、delivery 记录也生效；历史真实回复与错误接收者不改写。新活动不再生成“开始处理本轮任务”等固定开场事件，执行记录由已有的活动、模型运行和任务进度保存。
5. 当前活动收进输入区的一条简短状态提示，按用户后续要求移除暂停操作；移除“已接收、已送达、已答复”等气泡尾部噪声。进度显示当前专家和实际调用对应的业务动作，例如“材料拆解专家 · 阅读材料原文”，结束后消失，不估算虚假的完成百分比。普通任务弹窗同样不提供停止按钮，仅显示进度或失败信息；失败后的关闭和恢复入口仍保留。
6. 只有本轮执行了业务工作或需求理解内容实际变化，才在收尾生成理解确认请求。原有人工确认及成果写入保护继续生效。
