# PBS 场景拆分示例与验收方法

本文件把场景的拆分粒度、来源关系和未知事项转为可检查的业务样例。样例来自仓库内三份演示材料，不代表真实客户要求，也没有经过业务同事确认。

[设计](2026-10-20-scenario-requirements-design.md)中的字段和状态为本轮开发目标。这里给出的分组是一种可接受答案，验收允许其他语义等价的分组。

## 示例一 道路无人机巡逻标书

来源：[交警标书](../../../app/seed/samples/tender_police.md)。

| 场景候选 | 应保留的内容 | 对应原文 |
| --- | --- | --- |
| 定时道路巡逻与事件发现 | 无人值守、按时段巡逻、夜间车辆和人员辨识、四类事件识别 | 2.1.1、2.1.2、2.1.3、2.2.1 |
| 接警后飞抵现场与现场支援 | 一键起飞、实时视频、空中喊话疏导 | 2.1.2、2.3.1、2.3.2 |
| 违法车辆识别与取证 | 车牌识别、自动取证、材料可直接用于非现场执法 | 2.2.2 |
| 事件推送与处置工单生成 | 推送交警集成指挥平台、生成处置工单 | 2.2.3 |
| 指挥中心态势查看 | 视频上墙、GIS 一张图、PGIS 上展示事件和无人机位置 | 2.4.1、2.4.2 |

“现场支援”等名称是分析归纳；不得据此增加自动调度警力、自动结案等原文没有的行为。场景角色如果仅从采购单位或上下文推断，也应标明。

条款 2.1.2 同时支持“定时巡逻”和“接警后飞抵现场”。原始需求应分开表达两种触发条件，来源允许相同。不能因为引用重复只保留其中一个。

条款 2.2.1 至少需要完整保留交通事故、违停、拥堵、道路抛洒物四个对象，以及“不低于 90%”的要求。应提出如何定义识别准确率及验收数据集的问题；不得把不清楚的指标口径改写成已确定的逐类别指标或其他指标。

以下内容仍需有明确去向：

| 要求 | 处理方式 |
| --- | --- |
| -30℃～50℃、IP55 | 设备环境约束，关联适用场景，保留上下限 |
| 公安视频专网、安全边界接入、数据不少于 90 天 | 部署、安全、存储约束 |
| 等保三级及测评费用、国产化与适配证明 | 项目约束及对应交付要求 |
| 3 人驻场、8 名飞手取证、2 期培训、2 年免费运维含易损件更换 | 交付与服务 |
| 资质、项目业绩、付款比例、废标规则 | 商务与资格审阅清单 |

## 示例二 林区火点告警与护林员通知

来源：[森林防火纪要](../../../app/seed/samples/minutes_forest.md)。

以下是一个场景的完整表达示例。示例关联使用原文内容，不假定模型输出的 R 编号固定。

| 字段 | 内容 | 依据或未知 |
| --- | --- | --- |
| 名称 | 林区火点告警与护林员通知 | 对客户诉求的归纳 |
| 目标 | 将发现的火点告警与位置提供给应急平台，并通知附近护林员 | 客户诉求第 3 项 |
| 条件 | 林区巡查发现火点；需支持夜间火点发现 | 客户诉求第 1、2、3 项 |
| 角色 | 接收通知的附近护林员；具体值班处理角色未明确 | 原文没有规定平台值班岗位 |
| 触发 | 发现火点 | 客户诉求第 3 项 |
| 活动 | 形成火点告警及位置；推送县应急指挥平台；通知附近护林员 | 第 3 项，活动表述属于对原文的拆解 |
| 输出 | 平台收到告警及位置；护林员收到通知 | 发送渠道、时限、送达确认方式未知 |
| 支撑要求 | 护林员在手机上查看火点位置和无人机画面 | 客户诉求第 4 项 |
| 依赖 | 应急指挥平台接口开放情况；林区通信条件 | 待确认事项第 2 项、客户现状第 3 项 |
| 范围 | 包括告警推送与通知；通知后的处置闭环未明确 | 不自动补上派单、签收、结案 |

本场景需要的澄清至少包括：

1. 省建应急指挥平台是否开放接入接口，由谁确认、如何接入？
2. 无手机信号区域如何通知护林员，手机查看能力在哪些条件下可用？
3. 如何界定“附近”，通知哪些人员，是否有送达时限和回执要求？

这三项都属于需要确认的问题，不能预设平台支持标准接口、默认使用短信、默认 30 秒送达。

“发现烟火自动告警”“夜间发现火点”“最好测出温度”要保留不同要求强度，不能把“最好”升级为强制要求。火场长时间悬停监控与通信中继有不同触发条件及目标，应另设场景或明确的子场景，不能并入日常巡查后遗漏。

## 示例三 城管违建巡查与三维建模

来源：[城管口述](../../../app/seed/samples/oral_cityadmin.txt)。

建议至少区分两个业务目标：

- 中心城区每月巡查、历史影像对比、新增违建线索标记、按月报告、向街道派单核查处理。
- 为规划部门提供城区三维实景模型。

巡查场景需要保留约 80 平方公里、每月频次、历史影像条件与派单对象。原文“最好能跟去年的影像自动比对”表达期望能力，不代表去年影像已经可取得，应提出来源、质量和可用性问题。

客户没有飞手且希望我方提供飞行服务，因此交付边界包含服务。不能按默认产品采购思路改成客户自运营，也不能自行增加飞手培训或长期自有机队采购。

数据不得上互联网、放在局内机房，是两个业务目标适用的项目约束。“渣土车监管这次先不做”须保留为范围外，不能进入本期场景或 PBS。

## 验收方法

配套 [案例 JSON](2026-10-20-scenario-requirements-cases.json)提供每个检查项的原文、应保留内容和禁止补造的内容。它用于模型输出的人工检查和后续回归设计，不是已经通过的测试报告。

每个案例采用四种结果：通过、部分通过、不通过、未执行。记录具体遗漏、错误引用或人工修正，而不只打总分。

| 维度 | 判断方法 |
| --- | --- |
| 要求保留 | 对照检查项，统计被正确保留的对象、条件、数字和强度 |
| 来源对应 | 检查引用能否定位，且能否支持关联表述 |
| 场景合理性 | 能否解释谁在什么条件下达成什么目标，粒度是否便于业务审阅 |
| 未知识别 | 必要疑问是否显式保留，有无把未知转为事实 |
| 去向完整性 | 场景、约束、服务、商务、背景、范围外、待归类是否覆盖所有有效要求 |
| 修改成本 | 记录业务人员新增、删除、重写、重分组的数量与耗时 |

硬性失败包括虚构关键参数、范围外内容进入交付、引用不存在、人工成果被重生成覆盖、上游变化后相关 PBS 仍显示已确认。引用存在但不支持表述，也属于失败。

关键检查项必须逐项通过。普通措辞和场景分组允许业务人员判断等价，不以模型生成的固定条数验收。普通检查项记录通过数及分母，基线建立前不宣称提升比例。

为比较优化效果，保留相同的材料与模型配置；分别保存现有抽取/能力输出和新流程输出。每份材料至少运行两次观察波动，结果分别记录，不挑选最好的一次。正式阈值在业务人员审阅这套样例后确定。

本轮还运行了三份材料的实际分段、原文引用核对，以及编号条款续行的独立复现。结果记录于 [结构基线 JSON](2026-10-20-scenario-requirements-baseline.json)。

真实模型质量基线尚未运行，三个演示样例也未替代真实项目验收；不能把已有 34 项工程测试的通过率当成业务准确率。
